# 三路实时视频处理部署设备选型（4K 输入最低要求）

## 1. 目标与前提

本表针对当前项目的全流程模式（YOLO + ByteTrack + PaddleOCR + SCRFD/ArcFace + 可视化写出），结合你补充的摄像头规格（每路 `3840×2160`），目标为：

- 同时处理 3 路视频流
- 每路目标 4K（3840×2160）@25fps 实时
- 单机部署，长期稳定运行

## 2. GPU 策略结论（先回答是否需要多 GPU）

| 方案 | 是否建议用于 3 路 4K 实时 | 推荐配置 | 结论 |
|---|---|---|---|
| 单 GPU 统一调度 | 不建议作为生产最低方案 | 1×4090 24GB | 可用于开发验证和压测，但三路 4K 全流程长期稳定实时风险高（负载尖峰时易掉帧/排队）。 |
| 双 GPU 分担（2+1） | **建议作为最低生产方案** | **2×4090 24GB**（或同级） | 成本与稳定性平衡最好，建议路由为 GPU0 跑 2 路、GPU1 跑 1 路并预留余量。 |
| 三 GPU 一路一卡 | 可用但非最低必要 | 3×中高端 GPU | 性能最稳、隔离最好，但采购与运维成本更高，通常用于更高并发或高可用场景。 |

## 3. 各维度设备选型（最低可用，按 3 路 4K）

| 维度 | 最低要求 | 对应设备选型（建议型号） | 选型说明 |
|---|---|---|---|
| GPU（核心推理） | **至少 2 张 24GB 级 GPU** | **2×NVIDIA GeForce RTX 4090 24GB** | 3 路 4K 下，最低建议双卡分担；单 4090 不建议作为生产最低配置。 |
| CPU（解码/调度/后处理） | 24 核（或 16 核 32 线程）以上 | **Intel Core i9-14900K / AMD Ryzen 9 7950X** | 4K 解码、预处理、可视化写出会显著推高 CPU 压力，建议比 1080p 方案至少提高一档。 |
| 内存 | 128GB DDR5 | **4×32GB DDR5-5600** | 双 GPU + 3 路 4K 缓冲 + Python 多进程并发，64GB 在长时间运行下余量偏紧。 |
| 系统盘/数据盘 | 2TB NVMe SSD（建议 TLC） | **Samsung 990 PRO 2TB / WD SN850X 2TB** | 4K 视频文件与输出结果更大，持续写入更重，建议 2TB 起步。 |
| 主板 | 支持双 x16 物理槽位、足够 PCIe 通道、稳定供电 | **Z790/X670E 工作站级主板** | 双卡部署需关注槽位间距、供电、散热与带宽分配。 |
| 电源 | 1600W 80Plus Gold/Platinum | **Corsair HX1500i / Seasonic PRIME TX-1600** | 双 4090 + 高端 CPU 下建议预留足够瞬态功耗余量。 |
| 散热与机箱 | 高性能风冷/水冷 + 高风量机箱 | **360 水冷或双塔风冷 + 全塔风道机箱** | 长时推理负载对散热连续性要求高，温度过高会触发降频，直接影响实时性。 |
| 网卡/网络 | 千兆可用，建议 2.5GbE/10GbE | **Intel X550-T2（10GbE）** | 三路 4K 源流 + 管理流量 + 存储交互，建议提高网络余量避免瞬时拥塞。 |
| 操作系统 | Ubuntu 22.04 LTS | **Ubuntu Server 22.04.4 LTS** | 与 CUDA、驱动、Python 生态兼容度高，部署与运维成熟。 |
| NVIDIA 驱动 | 与 CUDA 12.x 兼容稳定版 | **Driver 550+（按官方兼容矩阵安装）** | 保障 torch / paddle / onnxruntime 的 GPU provider 正常工作，避免退回 CPU。 |
| Python 运行环境 | Python 3.10/3.11 + venv | **Python 3.10.14 + venv** | 与项目依赖兼容性更稳，减少版本冲突风险。 |
| 推理依赖（GPU） | CUDA 版深度学习栈 | **torch(CUDA) + paddlepaddle-gpu + onnxruntime-gpu** | 项目核心模块分别依赖不同推理后端，三者都必须走 GPU 才能满足实时目标。 |
| 视频编解码策略 | FFmpeg + H.264，建议启用硬编码 | **FFmpeg + h264_nvenc（优先）** | 当前若使用 x264（CPU）会提高 CPU 压力；启用 NVENC 可显著提升三路并发稳定性。 |
| 存储与结果目录规划 | 本地高速盘 + 分区目录 | **`/data/videos`、`/data/results`、`/data/logs`** | 目录隔离便于容量与性能管理，降低单目录大文件导致的维护成本。 |
| 进程管理与守护 | 系统级守护 + 自动拉起 | **systemd service + restart policy** | 生产环境必须具备崩溃自恢复能力，避免人工干预导致服务中断。 |
| 监控与告警 | GPU/CPU/内存/磁盘/进程监控 | **Prometheus + Node Exporter + DCGM Exporter + Grafana** | 双 GPU 场景要重点监控每卡利用率、显存峰值、GPU 温度与视频处理排队长度。 |

## 5. 最低验收基线（建议）

| 验收项 | 最低通过标准 |
|---|---|
| 实时性 | 3 路均达到接近实时（每路处理 FPS 不低于输入 FPS 的 0.95） |
| 稳定性 | 连续运行 8 小时无进程崩溃、无显存溢出、无明显帧处理堆积 |
| 资源余量 | 单卡 GPU 显存峰值不超过 90%，CPU 平均不超过 85%，磁盘写入无长时间阻塞 |
| 输出质量 | 输出视频完整可播放，检测/识别结果持续可用，无大面积漏标或错标突增 |

---

备注：如果你希望继续压低成本，可以采用“输入 4K、推理前统一缩放到 1920×1080、结果再映射回原图”的策略，这会把硬件需求显著拉回到单卡方案；但会带来小目标识别精度下降风险，需要单独做精度验收。
