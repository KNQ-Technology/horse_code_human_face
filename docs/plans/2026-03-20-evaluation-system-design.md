# 赛马识别系统端到端评测方案设计

> 创建日期：2026-03-20
> 状态：已通过评审

## 1. 评测范围与目标

**评测对象：** 系统的端到端输出——每个视频最终产出的 `(马号, 骑手)` 集合。

**评测目标：**

1. 量化系统在马号识别、骑手识别、配对准确性三个维度上的表现
2. 对错误进行归因分析，明确是哪个环节导致的失败
3. 为后续算法迭代提供优先级依据

**不在评测范围内的：** 检测框精度 (mAP)、追踪连续性 (MOTA)、OCR 字符级准确率等模块级指标。

## 2. Ground Truth 定义与标注格式

### 2.1 标注文件结构

整个评测集使用一个 JSON 文件 `ground_truth.json`，格式如下：

```json
{
  "version": "1.0",
  "annotator": "标注者姓名",
  "created_at": "2026-03-20",
  "videos": [
    {
      "video_file": "race_2026_03_15_R1.mp4",
      "race_info": {
        "date": "2026-03-15",
        "race_number": 1,
        "venue": "沙田"
      },
      "ground_truth": [
        {
          "horse_id": "B123",
          "rider_name": "潘顿",
          "notes": ""
        },
        {
          "horse_id": "A045",
          "rider_name": "莫雷拉",
          "notes": "短暂出现，约2秒"
        }
      ]
    }
  ]
}
```

### 2.2 字段说明

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `video_file` | string | 是 | 视频文件名，与评测目录中的文件名一致 |
| `race_info` | object | 否 | 赛事元信息，用于追溯和分组分析 |
| `horse_id` | string | 是 | 马号，格式与系统一致（如 `B123`） |
| `rider_name` | string | 是 | 骑手姓名，必须与人脸数据库中的注册名一致 |
| `notes` | string | 否 | 备注，记录特殊情况（遮挡严重、出现时间极短等） |

### 2.3 关键约束

- `rider_name` 必须使用系统人脸库中的**注册姓名**，避免因名称不一致导致误判
- 一个视频中同一马号不应重复出现
- 如果视频中某匹马的号码实在无法人工辨认，`horse_id` 填 `"UNKNOWN"`，该条在评测时单独统计

## 3. 标注工作流程

### 步骤一：准备工作

1. 将所有评测视频放入统一目录 `eval/videos/`
2. 收集每个视频对应的赛事官方出赛名单（马号→骑手映射表）
3. 导出系统人脸库中已注册的骑手姓名列表，作为 `rider_name` 的标准用词参考

### 步骤二：逐视频标注

1. 先查阅该视频对应的**官方出赛名单**，了解理论上有哪些马号和骑手
2. 完整观看视频，确认**实际出现**在画面中的马匹和骑手
3. 逐匹核对：视频中能看到的马号是什么、骑手是谁
4. 填入 `ground_truth.json`，注意：
   - 仅标注**实际出现在视频画面中**的马匹，不是名单上所有参赛马
   - 出现时间极短（<1秒）或完全被遮挡无法辨认的，在 `notes` 中注明

### 步骤三：交叉验证

- 标注完成后，由团队中的**另一人**抽查 30% 的视频进行复核
- 如有分歧，以讨论后的结论为准
- 记录分歧数量，作为标注一致性的参考指标

### 标注时间预估

- <20 个视频，每个视频预计 5-10 分钟（含观看 + 填表）
- 总计约 2-3 小时（含交叉验证）

## 4. 评测指标设计

### 4.1 基础指标（按视频计算）

对每个视频，将系统输出集合（Pred）与标注集合（GT）做集合比较，分三个维度：

| 维度 | Pred 集合 | GT 集合 | 说明 |
|------|-----------|---------|------|
| **马号** | 系统输出的所有 `horse_id` | GT 中的所有 `horse_id` | 忽略骑手，只看马号 |
| **骑手** | 系统输出的所有 `rider_name` | GT 中的所有 `rider_name` | 忽略马号，只看骑手 |
| **配对** | 系统输出的所有 `(horse_id, rider_name)` | GT 中的所有 `(horse_id, rider_name)` | 马号和骑手必须同时正确 |

每个维度计算：

- **Precision** = |Pred ∩ GT| / |Pred| — 系统输出中有多少是对的
- **Recall** = |Pred ∩ GT| / |GT| — GT 中有多少被系统找到了
- **F1** = 2 × Precision × Recall / (Precision + Recall)

### 4.2 汇总指标（跨视频）

- **宏平均 (Macro-Avg)**：所有视频的 P/R/F1 取算术平均
- **微平均 (Micro-Avg)**：将所有视频的 TP/FP/FN 累加后计算 P/R/F1（避免小视频权重过大）
- **完全匹配率 (Exact Match Rate)**：Pred 集合与 GT 集合完全一致的视频占比

### 4.3 错误归因分析

对每个错误分类统计：

| 错误类型 | 定义 | 排查方向 |
|----------|------|----------|
| **马号漏检 (Miss-Horse)** | GT 中有该马号，Pred 中没有 | 检测/追踪/OCR 失败 |
| **马号误检 (FP-Horse)** | Pred 中有该马号，GT 中没有 | OCR 误读/追踪漂移 |
| **马号错认 (Wrong-Horse)** | GT 中的马号 X 被系统识别为了马号 Y | OCR 混淆（如 B123→B128） |
| **骑手漏检 (Miss-Rider)** | GT 中有该骑手，Pred 中没有 | 人脸检测/识别失败 |
| **骑手误检 (FP-Rider)** | Pred 中有该骑手，GT 中没有 | 人脸误匹配 |
| **骑手错配 (Wrong-Pair)** | 马号和骑手各自都出现在 GT 中，但配对关系错误 | 追踪 ID 混淆/人脸分配错误 |

最终输出一个错误分布统计表，指明哪种错误最多，从而决定优先优化哪个模块。

## 5. 评测执行流程与输出

### 5.1 目录结构

```
eval/
├── videos/                     # 评测视频
│   ├── race_2026_03_15_R1.mp4
│   └── ...
├── ground_truth.json           # 人工标注文件
├── results/                    # 系统输出（自动生成）
│   ├── race_2026_03_15_R1_summary.json
│   └── ...
└── reports/                    # 评测报告（自动生成）
    ├── eval_report_2026-03-20.json
    └── eval_report_2026-03-20.md
```

### 5.2 执行步骤

1. **跑系统**：对 `eval/videos/` 下的所有视频执行现有流水线，输出 `_summary.json` 到 `eval/results/`
2. **跑评测脚本**：读取 `ground_truth.json` 和所有 `_summary.json`，自动计算全部指标
3. **生成报告**：输出结构化 JSON 报告 + 可读的 Markdown 报告

### 5.3 评测报告内容

Markdown 报告包含以下部分：

1. **总览表**：马号/骑手/配对三个维度的 Macro-Avg、Micro-Avg P/R/F1 + 完全匹配率
2. **逐视频明细表**：每个视频的 P/R/F1，按 F1 从低到高排列（最差的排最前，方便定位问题）
3. **错误归因统计**：6 种错误类型的数量 + 占比
4. **错误详情列表**：每条具体错误的视频名、GT 值、Pred 值、错误类型
5. **结论与建议**：根据错误分布，自动给出"建议优先优化 XX 模块"的文字总结

### 5.4 迭代使用方式

每次算法改动后：

1. 重新对评测视频跑系统 → 生成新的 `results/`
2. 重新跑评测脚本 → 生成新报告（带日期区分）
3. 对比前后报告的指标变化，验证改动是否有效
